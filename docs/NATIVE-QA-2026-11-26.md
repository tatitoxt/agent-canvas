# Native Canvas QA handoff — 2026-11-26

This note captures the native-only findings from the comparative WebKit/web QA pass. The resize fix itself lives in `web/src`; the items below are intentionally left for the Tauri/native owner.

## Terminal spawn: reproduced and isolated

The desktop shell is **not daemonless**: `src-tauri/src/main.rs` embeds the same `canvasd` core and exposes agent/PTY operations through Tauri commands/events. `web/src/daemon/tauriClient.ts` implements `spawn_agent`, `pty_input`, `pty_resize`, `snapshot`, and `transcript`; PTY bytes are relayed as base64 `canvas://pty` events.

The failing Finder/launchd path is the default repository root:

1. `pick_repo_root` falls back to `~/Canvas` when the process cwd is `/`.
2. setup creates and `git init`s `~/Canvas`, but does not create an initial commit.
3. agent spawning still tries to create a git worktree from `HEAD`.
4. a commitless repository has no `HEAD` target, so the spawn fails before a PTY exists.
5. the frontend only logs the rejected Tauri invocation to the console, so the click appears to do nothing.

Positive control performed with the same release binary:

```sh
CANVAS_REPO=/tmp/canvas-native-committed-yfA8 \
HOME=/tmp/canvas-native-home-iiNo \
src-tauri/target/release/bundle/macos/Canvas.app/Contents/MacOS/canvas-app
```

In that committed scratch repository, clicking the bottom-dock Terminal button immediately produced `Mission Map 1 live`, a `Terminal 1` card, visible `bash-3.2$` text, and this worktree:

```text
/tmp/canvas-native-committed-yfA8/.canvas-worktrees/744dd8f7ad31 [canvas/Terminal-744dd8f7ad31]
```

Recommended native fix (choose one or combine):

- for plain shells (`bash`/`zsh`/Terminal), spawn in the repository root instead of requiring a git worktree;
- or bootstrap an initial empty commit when creating `~/Canvas`;
- and surface `spawn_agent` invocation failures as user-visible notifications rather than `console.error` only.

## Resize defect fixed on the web side

Reproduction in Chromium/Playwright before the fix:

- bottom-right panel resize worked;
- resizing a panel outward from the top-left increased width/height but did **not** move the origin (`x/y`);
- the controlled store → React Flow reconciliation therefore restored the stale origin, making the card appear to snap back and grow toward the bottom/right, sometimes out of the viewport.

The root cause was not WebKit-specific clamping. `NodeResizer` reports changed `x/y` for top/left resizes, but panel, popped-out terminal, markdown, and web-page nodes discarded that position. Agent and workspace cards already passed it through.

The web fix now persists the resize origin for all those card types. Relevant validation:

- `npm run typecheck`
- `npm test -- --run` — 56/56 passing
- focused Playwright regression: `panel card resizing from the top-left keeps the resized origin instead of snapping back`
- focused terminal Playwright paths: pop-out, put-back, live PTY input, drawer resize — all passing

## Other Tauri observations

- `src-tauri/tauri.conf.json` uses `devUrl: http://localhost:5174`, while the Vite config uses port `5173`. Release builds embed `web/dist`, so this is probably only a dev-mode mismatch.
- `TauriCanvasClient.setAgentChain()` is currently a deliberate no-op in the desktop shell.
- Native WebKit localStorage for the current bundle lives under `~/Library/WebKit/com.canvas.desktop/.../LocalStorage/localstorage.sqlite3` (bundle id `com.canvas.desktop`). Older `com.canvas.app`/`canvas-app` WebKit directories appear stale.
- QA screenshots and accessibility evidence are under `/tmp/canvas-qa/`.
